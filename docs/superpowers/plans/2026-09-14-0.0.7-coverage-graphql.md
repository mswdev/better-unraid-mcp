### Task 1: `array_disk_action`

**Files:** Create `src/tools/array/array-disk-action.{graphql,ts,test.ts}`; modify `src/tools/registry.ts` (+1 mutating entry), `src/tools/registry.test.ts` (counts 41→42).

- `.graphql`: five operations — `ArrayDiskAdd($input: ArrayDiskInput!)` → `array { addDiskToArray(input: $input) { state } }`; `ArrayDiskRemove` likewise with `removeDiskFromArray`; `ArrayDiskMount($id: PrefixedID!)` → `array { mountArrayDisk(id: $id) { id status } }`; `ArrayDiskUnmount` likewise; `ArrayDiskClearStats($id: PrefixedID!)` → `array { clearArrayDiskStatistics(id: $id) }`; plus `ArrayStateProbe` → `array { state }` for the precondition read.
- Input: `action: z.enum(["add","remove","mount","unmount","clear_statistics"])`, `id: z.string()`, `slot: z.number().int().optional()` (add/remove only — reject elsewhere), `confirm`/`acknowledge_risk`, `response_format`.
- Preconditions (checked BEFORE the gate refusal? No — gate first, then precondition, so declining never costs a query): `add`/`remove` require array state `STOPPED`; `mount`/`unmount`/`clear_statistics` require `STARTED`. Wrong state → refusal naming the actual state and the fix (`array_action`).
- Result copy: "requested — verify with array_status/disk_list" (snapshot lesson).
- Tests: gate refusal runs zero queries; wrong-state refusal (executor returns STARTED for remove) issues only the probe; happy path per action asserts document + variables; `slot` rejected for mount; executor failure mapped.
- Annotations: `readOnlyHint:false, destructiveHint:true, idempotentHint:false, openWorldHint:false`; registry entry mutating.

### Task 2: `apikey_list` + `apikey_manage` (new `src/tools/apikey/`)

**Files:** Create `src/tools/apikey/apikey-list.{graphql,ts,test.ts}` and `src/tools/apikey/apikey-manage.{graphql,ts,test.ts}`; registry +2 entries (counts 42→44, read-only 24→25).

- `apikey_list` (read, ungated): `query ApiKeyList { apiKeys { id name description roles createdAt permissions { resource actions } } }` — deliberately does NOT select `key`, so secrets never enter the response path. Concise: one line per key (name, roles). Annotations read-only/idempotent.
- `apikey_manage` (tier-2): `action: z.enum(["create","update","add_role","remove_role","delete"])` with fields `name`, `description`, `roles: z.array(z.enum(["ADMIN","CONNECT","GUEST","VIEWER"]))`, `id`, `ids` (delete) — validated per action (e.g. create requires `name`, add_role requires `id` + exactly one role). Operations: `ApiKeyCreate($input: CreateApiKeyInput!) { apiKey { create(input:$input) { id name key roles } } }`, `ApiKeyUpdate`, `ApiKeyAddRole`, `ApiKeyRemoveRole` (Boolean!), `ApiKeyDelete` (Boolean!).
- Creation is the single sanctioned key disclosure: success text `Created API key "<name>" (id …). Key value (shown once, store it now): <key>` — phrased to dodge the redactor's key-value pattern; a test proves the value survives `toolText` redaction and another proves an `apiKey`-shaped echo elsewhere still redacts.
- Description says plainly the model is managing credentials; delete warns it may lock out the very key this server uses.
- Tests: per-action validation errors; gates; happy paths (document + variables); create discloses key once.
