# 0.0.9 "Live + Launch" Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship release 0.0.9 — a graphql-ws subscription client feeding a live snapshot store, subscribable MCP resources (parity, docker stats, metrics, log follow), a subscription-preferring `docker_stats`, and the launch kit (README overhaul + forum post draft).

**Architecture:** `SubscriptionFeed` wraps `graphql-ws`'s client (lazy connect, `graphql-transport-ws` subprotocol, `connectionParams: {"x-api-key": <key>}` — the API's auth guard merges connectionParams into request headers; `ws` as the WebSocket impl for Node 20) behind an injectable socket-client seam so tests use a scripted fake. Live samples land in a `LiveSnapshotStore` (topic → {data, receivedAt}). `registerLiveResources` declares the `resources.subscribe` capability, registers four subscribable resources, handles `resources/subscribe`/`unsubscribe` via the low-level `setRequestHandler`, starts/stops feed subscriptions per subscribed URI, and emits `notifications/resources/updated` on each sample. `docker_stats` prefers a fresh live sample (≤ 10 s) and says so; otherwise the SSH path runs and says that.

**Tech Stack:** + `graphql-ws` and `ws` (runtime deps), `@types/ws` (dev).

**Spec:** `docs/superpowers/specs/2026-09-14-competitive-roadmap-design.md` (Phase 6 section)

## Global Constraints

- Branch `feature/0.0.9-live-launch` off `develop`; repo hard limits + quality gate.
- Confirmed subscription fields (SDL 3697–3715): `dockerContainerStats`, `logFile(path)`, `systemMetricsCpu/Memory`, `arraySubscription`, `parityHistorySubscription`.
- Server-initiated resource-updated notifications reach stdio and session-mode HTTP clients only (spec §4) — docs say so.
- The feed is created only when needed (a subscribable resource is first subscribed, or docker_stats probes it) — no WS connection at startup.

## Tasks

### Task 1: deps + `SubscriptionFeed` (`src/graphql/subscription-feed.ts` + test)
- `npm install graphql-ws ws && npm install -D @types/ws`.
- Produces: `interface FeedHandlers { onData(data: unknown): void; onError?(error: unknown): void }`, `class SubscriptionFeed { constructor(options: SubscriptionFeedOptions); subscribe(query: string, variables: Record<string, unknown> | undefined, handlers: FeedHandlers): () => void; dispose(): void }` with `interface SubscriptionFeedOptions { endpoint: string; apiKey: string; createClient?: CreateClientLike }` — `CreateClientLike` mirrors graphql-ws's `createClient` signature subset (`{ subscribe(payload, sink): () => void; dispose(): void }`). Real path: `createClient({ url: toWsUrl(endpoint), connectionParams: { "x-api-key": apiKey }, webSocketImpl: WebSocket_from_ws, lazy: true, retryAttempts: RETRY_ATTEMPTS (named 10), shouldRetry: () => true })`. `toWsUrl` maps http(s)→ws(s), exported for tests.
- Tests (fake client): subscribe passes query/variables and pumps `next` data to onData; errors go to onError without throwing; unsubscribe calls the sink-returned disposer; `toWsUrl("https://x/graphql") === "wss://x/graphql"`; the real client is only constructed on first subscribe (lazy).

### Task 2: `LiveSnapshotStore` (`src/graphql/live-store.ts` + test)
- `class LiveSnapshotStore { constructor(now?: () => number); set(topic: string, data: unknown): void; get(topic: string): { data: unknown; ageMs: number } | null }`. Tests: set/get with age from injected clock; unknown topic → null.

### Task 3: Live resources (`src/resources/live-resources.ts` + test; wire in `src/server.ts` behind `options.feed`)
- `RegistryOptions` gains `feed?: SubscriptionFeed | null; liveStore?: LiveSnapshotStore` (built in `src/index.ts`: feed only when `UNRAID_API_URL` is set — always — so unconditionally; store shared).
- Resources (all `application/json`): `unraid://live/parity` (topic `parityHistorySubscription`, subscription document `subscription { parityHistorySubscription { ... } }` as raw strings — no codegen for subscriptions), `unraid://live/docker-stats` (`dockerContainerStats`), `unraid://live/metrics` (`systemMetricsCpu` + `systemMetricsMemory` merged under one topic pair), and template `unraid://logs/{path}` (`logFile(path:)`).
- Read callback: latest store sample (`{ data, age_ms }`) or `{ waiting: true, hint: "subscribe to this resource (or call the matching tool) — live samples arrive over WebSocket" }`.
- Subscribe handling: `server.server.registerCapabilities({ resources: { subscribe: true, listChanged: true } })` before connect (in registration path); `setRequestHandler(SubscribeRequestSchema)` starts a feed subscription for the URI's topic (idempotent per URI), stores the unsubscribe; on each sample: `store.set(topic, data)` + `server.server.sendResourceUpdated({ uri })` (failures swallowed); `UnsubscribeRequestSchema` stops it.
- Tests with fake feed + fake low-level server: subscribe request starts exactly one feed subscription; a pumped sample updates the store and sends one updated notification with the right uri; unsubscribe stops (feed unsubscribe called); a second subscribe to the same uri does not double-subscribe; logs template extracts the path variable into `logFile` variables.

### Task 4: `docker_stats` prefers live data (`src/tools/docker/docker-stats.ts` + test)
- Handler factory gains optional `liveStore?: LiveSnapshotStore | null`; named `LIVE_FRESHNESS_MS = 10_000`. If a `dockerContainerStats` sample is ≤ fresh, respond from it with source line `(source: live subscription, age Xms)`; else run the SSH path and append `(source: ssh)`. Registry passes the store.
- Tests: fresh sample served without any shell call; stale/absent sample falls back to SSH and says so.
